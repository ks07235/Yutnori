# 윷놀이 앱 UI/UX 경험과 시행착오

작성: 2026-10-21 (한국 시간) · ks07235의 사용자 피드백과 Codex의 구현·검증 기록 정리

이 문서는 실제 윷을 던진 결과를 입력해 사용하는 Android 윷놀이 보드 앱을 다듬으며 얻은 판단 기준이다. 다음 앱에서도 재사용할 수 있도록 **불편했던 상황 → 시행착오 → 채택한 방법 → 배운 점**으로 정리했다. 사용자 체감 의견과 자동 테스트 결과는 서로 다른 근거로 취급한다.

## 1. 먼저 기억할 원칙

1. 게임 규칙과 좌표의 정확성이 장식·효과보다 먼저다.
2. 화면의 크기가 아니라 사용자가 실제로 쓸 수 있는 영역을 기준으로 배치한다.
3. 글씨를 키웠다는 코드보다 실제 화면에서 읽히는지가 중요하다.
4. 색, 모양, 위치, 텍스트를 함께 써서 상태를 구분한다.
5. 접힌 영역의 공간은 주요 콘텐츠에 돌려주고, 펼치는 버튼은 항상 찾을 수 있게 한다.
6. 상태는 먼저 확정하고 애니메이션은 그 상태를 보여준다.
7. 짧은 연출도 중단·건너뛰기·동작 줄이기·음소거를 고려한다.
8. 기본값과 자동 복원에도 사용자의 선택권과 탈출 경로를 남긴다.
9. 같은 기종에서도 화면 배율·글씨·카메라·내비게이션 설정이 다르면 다른 화면이다.
10. 구현 완료, 자동 검증, 실제 기기 확인, 스토어 배포를 같은 말로 묶지 않는다.

## 3. 회전해도 말과 도착 화살표가 칸의 중심에 있어야 한다

**불편:** 세로에서 가로로 바꿀 때 판은 넓어졌는데 말과 이동 미리보기 화살표가 원형 칸의 중심에서 어긋나는 피드백이 반복됐다. 같은 기종에서도 다르게 보였다.

**시행착오:** 특정 기기의 오프셋이나 화면 비율을 맞추는 것만으로는 판, 말, 터치 영역이 서로 다른 좌표계를 쓰는 문제를 막을 수 없다. 회전 전 픽셀 좌표를 기억하거나, 레이아웃이 끝나기 전에 새 좌표를 잡으면 다시 어긋날 수 있다.

**채택:** 게임은 칸 번호와 경로를 기억한다. `BoardGeometry`를 기준으로 판 그림과 오버레이가 같은 정사각형 영역을 쓰고, 레이아웃 후 칸 중심에서 말·도착지·터치를 함께 재계산한다. 실제 경로와 지름길은 `BoardPath`가 계산한다.

```text
게임 상태: 말 → 칸 ID + 경로
화면 상태: 실제 판 영역 + 현재 말 크기
배치 결과: 같은 칸 중심 → 말 / 화살표 / 터치 판정
```

**배운 점:** 좌표가 있는 UI는 위치의 의미와 픽셀을 분리해야 한다. 회전뿐 아니라 패널 접기, 창 크기 변경, 폴더블 펼침에도 같은 원칙을 적용한다. 화면 재배치는 게임 이동으로 취급하지 않는다.

**검수:** 반복 회전, 이동·잡기·골인 도중 회전, 패널 변경, 작은 휴대폰, 태블릿, 큰 글씨, 화면 재생성까지 본다. 모든 실기기에서 완벽하다고 단정하지 않는다.

## 4. 출발점을 옮길 때는 그림과 규칙을 분리한다

**불편:** 기존 출발점의 방향이 익숙한 윷판과 달라 보였고, 출발 안내도 어느 칸을 가리키는지 불명확했다.

**시행착오:** 보이는 판만 회전하거나 화살표만 바꾸면 말의 이동 순서·지름길·빽도는 이전 기준에 남을 수 있다. 사용자 설명에서 시계 방향과 반시계 방향 표현이 서로 엇갈린 적도 있었다.

**채택 방향:** 최종 경로 정의를 기준으로 판의 시작·출구와 각 분기점을 맞추고, 장식 화살표는 그 경로를 설명하게 한다. 출발 표시는 출발 원 가까이 두고 일반적인 제목처럼 떨어뜨리지 않는다.

**배운 점:** ‘오른쪽 아래’, ‘5시’ 같은 말은 보조 설명이다. 구현 계약에는 출발·종점·모퉁이·중앙의 노드 ID와 허용 경로를 함께 적는다. 그림의 회전과 규칙 변경을 같은 것으로 가정하지 않는다.

## 5. 방향 안내를 더해도 원래 경로선은 남아야 한다

**불편:** 방향 화살표를 더한 뒤 노드 사이의 선이 사라진 것처럼 보여 길을 읽기 어려워졌다. 화살표가 많거나 칸을 가려도 오히려 불편했다.

**채택 방향:** 출발과 갈림길을 우선해 작게 표시한다. 화살표는 노드를 잇는 선 옆 여백에 평행하게 놓되 보드 안쪽에서 잘리지 않게 한다. 원형 노드와 기본 경로선이 먼저 읽혀야 한다.

**배운 점:** 안내는 기존 구조를 보조해야 한다. 선·노드·말·강조·화살표의 그리기 순서와 여백을 따로 검토한다. ‘화살표가 보인다’와 ‘경로가 더 이해된다’는 다른 검사다.

## 6. 공간을 확보하면 안쪽 요소도 다시 배분한다

**불편:** 가로 화면 위아래 여백을 줄여 윷판이 커졌지만 현황판과 진행판의 내부 요소는 이전 간격에 머물렀다. 공간은 생겼는데 답답하거나 비어 보였다.

**시행착오:** 외곽 패널만 늘리고 안의 행·글씨·말 크기는 고정하면 공간 활용이 좋아지지 않는다. 반대로 모든 것을 비례 확대하면 버튼이나 4번째 팀이 잘린다.

**채택:** 현황판·윷판·진행판의 역할을 분리한다. 실제 현황 목록 영역 높이와 팀 수로 행 높이·간격을 정하고, 작은 높이에서는 스크롤로 접근성을 확보한다. 윷판의 정사각형 비율과 조작부의 최소 크기를 함께 지킨다.

**배운 점:** 바깥 여백 변경은 내부 정보 밀도를 다시 설계할 기회다. 남는 공간의 배분 순서를 정해야 한다. 이 앱에서는 판의 크기, 현재 팀·시간 가시성, 조작 버튼 순으로 판단했다.

## 7. 접기 기능은 공간뿐 아니라 상태 전환 문제다

**불편:** 정보와 입력을 접거나 펼친 뒤 다른 패널을 열면 컨트롤이 사라지거나 다시 접어야 보인다는 피드백이 있었다. 접힌 영역의 공간이 판에 돌아오기를 기대했다.

**시행착오:** View의 보임/숨김만 바꾸면 남아 있는 제약·부모·예약 레이아웃 때문에 빈자리와 중복 부착이 생길 수 있다. 조작부 접힘과 사용 가능한 윷 결과를 같은 상태로 묶어도 예측하기 어려워진다.

**배운 점:** 패널 열림 상태, 컨트롤의 소속 부모, 가용 판 영역을 함께 갱신한다. 펼치기 버튼은 카메라나 다른 패널 뒤로 들어가면 안 된다. 접고 펼치는 왕복과 다른 상태와의 조합을 테스트한다.

**현재 채택 범위:** 최종 리팩토링 기준에서는 현황판을 항상 보여주고, 가로의 조작부는 고정하며 세로 입력부를 접고 펼친다. 초기의 ‘가로·세로에서 모든 창 접기’ 요구를 현재 구현으로 기록하지 않는다. 다음 프로젝트에서 양쪽 접기를 도입할 때는 별도 상태 조합을 설계한다.

## 8. 같은 기종이어도 안전 영역과 글씨 배율이 다르다

**불편:** 카메라 홀이 접기 버튼을 가렸고, 일부 폰의 가로 화면에서 배치가 달랐다. 시스템 글씨 크기의 영향도 받았다.

**채택:** 카메라 컷아웃, 보이는 내비게이션 바, 제스처 영역을 실제 Insets로 처리한다. 왼쪽·오른쪽 카메라 위치를 모두 본다. 반복 전달되는 Insets는 원래 여백을 기준으로 계산해 누적하지 않는다.

**시행착오에서 얻은 판단:** 화면 위아래를 전부 빼면 중요한 판 영역까지 작아질 수 있다. 배경이 사용할 영역과 버튼이 피해야 할 영역을 구분하되, 기기별 예외를 임의의 고정값으로 추가하지 않는다.

**배운 점:** 기종명이 같다는 사실은 UI 동등성의 근거가 아니다. 화면 방향, 실제 가용 dp, 글씨·화면 배율, 시스템 바, 멀티윈도우를 함께 기록한다.

## 9. ‘글씨를 키웠는데 안 커졌다’는 최종 적용 경로 문제다

**불편:** 진행판의 도·개·걸·윷·모 글씨를 키웠다고 했는데 실제로는 달라 보이지 않았다. 시작 화면과 설정에서도 글씨 크기·줄바꿈 피드백이 이어졌다.

**확인할 원인:** XML의 크기 뒤에 코드의 `setTextSize`, AutoSize, 큰 글씨 보정이 다시 적용되는지 본다. 컨테이너가 그대로 작으면 AutoSize가 글씨를 다시 줄일 수도 있다. 현재 앱에는 이런 복수의 크기 적용 경로가 있다. 개별 과거 피드백의 단일 원인을 모두 확정한 것은 아니다.

**채택:** 가로/작은 높이/큰 글씨를 구분하고 제목·설명·행동 버튼의 위계를 정한다. 문장을 의미 단위로 줄바꿈하고, 긴 설명은 스크롤하되 적용·닫기 버튼은 접근 가능하게 한다.

**배운 점:** 운영체제 글씨 설정을 무조건 무시하는 방식보다 읽을 수 있는 최소 크기와 재배치·스크롤을 함께 설계한다. 확대 결과를 코드 diff가 아니라 실제 측정된 화면으로 확인한다.

## 10. 가로 화면은 넓게 늘인 세로 화면이 아니다

**불편:** 시작 화면과 말 꾸미기가 지나치게 옆으로 길고 위아래가 비었다. 큰 창인데 팀 이름·말 미리보기는 작게 느껴졌다. 일부 확인창은 기본 스타일에 남아 분위기가 달랐다.

**채택:** 가로 기본 사용을 반영하되 설정에서 방향 선택을 유지한다. 시작 화면의 폭을 제한하고 버튼을 도톰하게 한다. 말 꾸미기는 팀 목록·색·모양을 나란히 배치하고, 팀 이름과 실제 말 미리보기에 더 많은 높이를 준다. 작은 높이·큰 글씨에서는 스크롤을 허용한다.

**배운 점:** 가로 화면에서는 폭을 다 쓰는 것보다 시선 이동 거리를 줄이는 편이 좋을 수 있다. 첫 화면에서 팀 선택, 꾸미기, 시작이라는 순서가 자연스럽게 읽혀야 한다.

## 11. 팀 수가 바뀌면 전체 묶음을 다시 정렬한다

**불편:** 4팀에서는 마지막 팀이 다시하기 버튼과 겹쳤고, 2·3팀에서는 위부터 채워져 현황판이 불균형했다.

**채택:** 목록과 하단 행동 버튼을 별도 영역으로 나누고, 실제 목록 높이를 기준으로 행을 계산한다. 참여 팀 수에 맞는 전체 묶음을 중앙 정렬하되, 공간이 부족하면 스크롤로 모든 팀을 볼 수 있게 한다.

**배운 점:** ‘항목 하나가 잘 보인다’만 검사하면 목록 전체의 균형과 마지막 항목 충돌을 놓친다. 2·3·4팀, 시간전·무제한전, 작은 가로 높이를 조합해서 본다.

## 12. 상태는 색만으로 전달하지 않는다

**불편:** 현재 팀, 업힌 말 수, 골인한 말을 멀리서 바로 알아보기 어려웠다. 밝은 말에서는 숫자·X의 대비도 중요했다.

**채택:** 현재 차례에 해당 팀의 실제 말 색과 모양을 함께 보여준다. 업힌 말은 개수에 따른 배치를 사용하며 이동할 때 모였다가 도착 후 펼친다. 골인 X는 최초 폭 36%에서 최종 72%로 키우고 선은 지름의 12%로 다듬었다. 밝은 말에는 어두운 표시를 쓴다.

**보류한 실험:** 업힌 말을 더 크게 하거나 경로 방향에 따라 X2 같은 숫자를 말 옆에 두는 안은 별도 비교 후 판단하기로 했다. 초기 요구를 그대로 최종 적용했다고 쓰지 않는다.

**배운 점:** 가까이 보는 개인 앱과 여러 사람이 멀리서 보는 공유 화면의 가시성 기준은 다르다. 색상 수를 늘리는 것보다 모양·대비·크기·상태 표식을 함께 조절한다. 터치 영역은 시각 크기와 별도로 확장하되 인접 노드와 겹칠 때 가까운 노드를 판별한다.

## 13. 용어와 행동 버튼은 사용자의 기대를 맞춰야 한다

**불편:** 톱니바퀴만으로는 게임 규칙 설정인지 알기 어려웠고, 일시정지가 말 조작도 막는지 불명확했다. 다시하기와 메인으로 나가기도 한 창에 섞여 이해하기 어려웠다. 나가기 글씨의 대비 문제도 있었다.

**채택:** 규칙은 아이콘과 ‘게임 규칙’ 같은 이름·요약을 함께 보여준다. 시간만 정지하는 동작은 ‘시간 멈춤’으로 표현한다. 다시하기와 나가기를 별도 버튼·확인창으로 나누고, 팀·꾸미기·규칙·시간을 유지하는 초기화와 팀 선택으로 돌아가는 행동을 구분한다. 나가기의 배경과 글씨 대비를 명시한다.

**배운 점:** 버튼 이름은 기술적 동작이 아니라 사용자가 기대하는 결과를 설명해야 한다. 확인창은 행동의 차이를 짧게 설명하고 기본 팝업 하나만 다른 스타일로 남겨두지 않는다. 파괴적 행동에는 취소 경로를 제공한다.

## 14. 한국적인 분위기는 읽기 쉬운 정보 위에 얹는다

**요구:** 설정창도 단순한 정보 나열보다 윷놀이 분위기를 느끼게 하되 글씨가 분명하게 보여야 했다.

**채택 방향:** 청록·먹색의 제목과 구분선, 통일된 창·버튼 표현으로 분위기를 맞춘다. 장식보다 제목·설명·선택 상태의 대비와 문단 구분을 우선한다. 말 색 선택은 단순 장식이 아니라 게임 중 식별성과 연결한다.

**배운 점:** 지역적 분위기를 복잡한 문양이나 어려운 서체로만 만들 필요는 없다. 작은 화면에서는 색·선·여백·일관된 말 모양이 더 안정적이다. 중요한 설명은 이미지 속 글씨가 아니라 읽고 확대할 수 있는 텍스트로 유지한다.

## 15. 미리보기와 연출은 다음 행동을 돕고 언제든 끝낼 수 있어야 한다

**요구:** 윷 결과를 선택하면 움직일 말을, 말을 고르면 도착 칸을 자연스럽게 보게 하고 싶었다. 잡기는 조금 익살스럽게, 우승 기록은 엔딩 크레딧처럼 보여주되 건너뛸 수 있기를 원했다.

**채택:** 선택 가능한 말과 도착지를 순서대로 강조한다. 잡기는 약 600ms의 눌림·흔들림·복귀 연출을 사용한다. 승리 크레딧은 건너뛰거나 터치해서 정적 결과로 전환하고, 끝난 뒤에도 결과를 읽을 수 있다. 동작 줄이기·화면 읽기·애니메이션 비활성화에서는 정적 표시를 지원한다.

**배운 점:** 효과의 역할은 ‘멋있음’과 ‘다음에 무엇을 누를지 알게 하기’를 구분해 평가한다. 종료 후 정보를 사라지게 하지 않고, 스킵이 결과까지 닫아버리지 않게 한다. 반복·과도한 펄스는 실제 사용자에게 검수받는다.

## 16. 보기 좋은 애니메이션도 상태 확정의 주인이 되면 안 된다

**문제:** 이동·잡기·골인 도중 화면을 돌리거나 앱을 나가면 오래된 완료 콜백이 남을 수 있다. 그 콜백이 턴·보너스·승리를 다시 처리하면 화면 문제를 넘어 게임 규칙이 깨진다.

**채택:** 이동 성공 후 엔진 결과, 시간·보너스, 기록·통계, 승리 대기 상태를 먼저 확정하고 저장한다. 애니메이션은 표시만 담당한다. 중단 시 세대 번호로 이전 콜백을 무효화하고 확정된 상태로 다시 그린다. 취소는 논리 상태를 먼저 되돌리고 역경로를 보여준다.

**배운 점:** UX의 안정성은 화면 코드만으로 보장되지 않는다. 게임 수명, 화면 수명, 한 번의 표시 작업 수명을 나누고 각자 정리할 리스너와 콜백을 소유하게 한다. 타이머도 수동 정지·창에 의한 보류·애니메이션 보류를 구분한다.

## 17. 소리와 진동도 독립적인 UX 기능이다

**시행착오:** 기존 전자음은 사건의 성격을 충분히 구분하지 못했고, 잡기 피드백이 애니메이션 함수 안에 있어 동작 줄이기에서 누락될 수 있었다.

**빌드 68의 로컬 적용:** 나무 타격감의 조작·선택·이동음, 짧은 익살스러운 잡기음, 국악풍 5음계의 골인·우승음을 자체 합성했다. 소리와 진동 설정은 독립적으로 유지하고 앱을 나가거나 음소거하면 재생을 멈춘다. 파일 준비 전 입력은 나중에 몰아서 재생하지 않는다.

**배운 점:** 시각 효과를 끄는 설정이 소리·진동까지 끄는 설정은 아니다. 의미 있는 사건에 짧게 반응하고, 미디어 볼륨과 게임 내 소리 끄기를 존중한다. 파형·재생 API 테스트 통과와 실제 스피커에서 듣기 좋은지는 별도로 확인한다.

## 18. 저장·업데이트·버전 표시도 사용자 경험이다

**불편:** 몇 주 전에 하던 게임이 자동으로 복원되거나, 게임 화면에 머물러 최신 버전 여부와 메인으로 돌아가는 길을 찾기 어려웠다. APK 파일명과 실제 설치 버전도 혼동됐다.

**채택:** 실제 버전·빌드를 표시하고 복사할 수 있게 한다. 오래된 저장 게임은 이어하기 선택을 확인한다. 현재 코드의 확인 기준은 24시간이다. 메인 복귀 경로를 제공하고, 업데이트는 사용 가능한 버전을 확인했을 때 선택적으로 안내한다. 이동·확인창 등과 안내가 충돌하지 않게 대기 상태를 둔다.

**배운 점:** 자동 복원은 편의일 수 있지만 사용자의 의도를 대신 결정해서는 안 된다. 버전은 파일 이름이 아니라 설치된 내부 값을 기준으로 확인한다. 네트워크·계정·배포 트랙 조건이 충족되지 않은 상태를 ‘최신 버전’으로 오해시키지 않는다. 스토어의 심사·배포 상태는 별도로 확인한다.

## 19. 변경 전후를 어떻게 확인했나

| 검사 축 | 실제 사용한 방법 | 한계 |
| --- | --- | --- |
| 게임 정확성 | 순수 엔진·경로·통계·타이머 테스트 | 예쁜지, 손에 편한지는 증명하지 못함 |
| 화면 배치 | Robolectric native 화면 검사와 PNG, 작은 가로 높이·큰 글씨·태블릿 배치 | 모든 제조사의 실기기 렌더링과 같다고 보장하지 못함 |
| 구조 분리 전후 | 기준 PNG 25개 비교, 상태·취소·회전 검사 | 버전 표시를 바꾸기 전 비교 결과와 바꾼 후 화면 차이를 구분해야 함 |

단순 파일 분리와 성능 개선도 구분했다. `MainActivity`의 줄 수 감소는 구조 지표다. 타이머 60회 갱신에서 불필요한 행 크기 갱신 요청을 줄였다는 결과를 FPS·배터리 개선 수치로 바꾸어 말하지 않는다.

## 20. 앞으로 다른 앱에서 사용할 작업 순서

1. **사용 상황을 먼저 적는다.** 누가, 얼마나 떨어져서, 어떤 방향으로, 무엇을 반복해서 누르는가.
2. **불변 조건을 적는다.** 상태·좌표·버튼 역할·취소·저장·접근 경로 중 무엇이 반드시 유지돼야 하는가.
3. **문제를 재현할 환경을 기록한다.** 버전/빌드, 가용 크기, 방향, 글씨 배율, 시스템 바, 현재 상태를 함께 남긴다.
4. **서로 연관된 수정은 묶는다.** 배치·글씨·컨테이너 문제를 함께 분석하고 논리적 변경 묶음 단위로 검증한다.
5. **정상 화면보다 전환을 검사한다.** 회전 왕복, 펼침/접힘, 취소, 앱 이탈·복귀, 항목 수 변경을 본다.
6. **자동 검증과 실제 체감을 구분한다.** 테스트·스크린샷은 안전망이고 사용자의 읽기·누르기·듣기는 별도 확인이다.
7. **판단을 남긴다.** 채택한 안, 보류한 안, 허용한 호환성 손실, 검증하지 못한 환경을 기록한다.
8. **배포와 협업을 마무리한다.** 개발 현황, 내부 버전, 작업 브랜치, 산출물, 검증 결과를 함께 전달한다.

작업 중 설명을 과하게 반복하는 대신, 기획에서는 선택 근거를 충분히 논의하고 구현에서는 묶음 단위로 짧게 보고했다. 성공한 검사를 이유 없이 반복하지 않되 새 수정·실패·미해결 위험이 생기면 관련 검증을 다시 수행한다. 토큰 절약이 정확성이나 검증 생략을 뜻하지는 않는다.
